## 1. Establish a clean experimental branch

The completed `codegen/fused-reduce` branch has been fast-forwarded into `main`; `c465f89` is therefore the pilot's product baseline. Start one isolated requirements branch from that exact commit. Initially add only new specification files and scripts, leaving product behavior unchanged until the final end-to-end pilot step.

The two generated evidence rewrites observed before the merge were produced against `9044b46`, not `c465f89`. They are preserved outside the baseline and are not eligible evidence for this plan.

The experiment was organized as six logical stages (split into reviewable
commits where necessary):

1. Requirements kernel.
2. Three pilot problem frames.
3. Observation/evidence bridge.
4. Derived status and work frontier.
5. Mutation calibration.
6. One existing product candidate replayed through the complete loop, followed
   by one prospective frozen cycle before scale.

No migration of the existing 590 rows until this experiment passes.

## 2. Add the minimum specification kernel

Create:

```text
Tgrad/Requirements/
  World.lean
  Phenomena.lean
  Assumptions.lean
  Requirements.lean
  ProblemFrames.lean
  Obstacles.lean

Tgrad/Specification/
  Boundary.lean
  Adequacy.lean

Tgrad/Conformance/
  Claims.lean

Tgrad/Evidence/
  Observations.lean
  Promotion.lean
```

Enforce dependency direction:

```text
Requirements ──→ Specification
                      ↑
Product ───────→ Conformance ──→ Evidence ──→ Derived State/Work
```

Important constraints:

- `Requirements/*` must not import concrete Tgrad product modules.
- Requirements may mention Python calls, tensors, values, errors, effects and devices.
- They may not mention `UOp`, `Renderer`, `PythonFFI`, or particular files.
- `Conformance/*` is the bridge allowed to import both the abstract specification and concrete product.
- Evidence never directly changes requirement status; promotion derives it.

The initial core can remain small:

```lean
inductive Controller
  | environment
  | machine

structure Phenomenon where
  id : String
  controlledBy : Controller
  description : String

structure Assumption where
  id : String
  statement : String
  provenance : String

structure Requirement where
  id : String
  frame : FrameId
  profile : ProfileId
  monitored : List PhenomenonId
  controlled : List PhenomenonId
  assumptions : List AssumptionId
  relation : Relation
  provenance : List SourceRef

structure MachineSpec where
  id : String
  observes : List PhenomenonId
  controls : List PhenomenonId
  relation : Relation

structure AdequacyObligation where
  assumptions : List AssumptionId
  specification : SpecId
  requirement : RequirementId
  status : Epistemic AdequacyResult
```

`Relation` must begin as a typed descriptor—not another unstructured string.
For the pilot, a modest algebra is enough, but this does not yet make it an
executable relation over traces:

```lean
inductive Relation
  | importResolves
  | samePublicNames
  | exactTensor
  | numericalTensor (rtol atol : Float)
  | sameShape
  | sameDtype
  | sameException
  | sameEffects
  | conjunction (relations : List Relation)
```

Later this can graduate into propositions and executable semantics.

## 3. Model three pilot requirements

Choose three because they cross different problem frames and correspond to known real failures.

### A. Python substitution

`REQ-PY-IMPORT-HELPERS`

World requirement:

> Under the public-API profile, a client importing `tinygrad.helpers` after substitution resolves to Tgrad without silently importing upstream tinygrad and exposes the declared public names.

Shared phenomena:

- Module request.
- Resolution result.
- Exported names.
- Import exception.
- Provenance of loaded module.

Baseline diagnosis at `c465f89`: failed or absent under the earlier observer.

This captures the blocker that caused 29 collection failures in the `fdc741d`
measurement. The suite has not yet been rerun on the current observed subject.

### B. Broadcasted addition

`REQ-TENSOR-ADD-BROADCAST`

World requirement:

> For compatible input tensors, substituted `Tensor.add` returns a tensor with the same shape, dtype, values, exceptions, and realization-observable effects as the declared tinygrad profile.

Shared phenomena:

- Input values, shapes and dtypes.
- Operation arguments.
- Returned shape and dtype.
- Realized values.
- Exceptions.

Baseline diagnosis:

- Product implementation exists.
- Upstream-suite observation is blocked by substitution prerequisites.
- Independent NumPy/differential evidence may establish only a narrower semantic claim.

Current model-level diagnosis: a candidate is mapped, but broadcast addition
remains unobserved through this requirements observer. The prerequisite's
isolated pass does not imply that the upstream suite now reaches this behavior.

That distinction tests whether the model can say “implemented and locally observed, but not yet observed through the compatibility boundary.”

### C. View readback and lifetime

`REQ-VIEW-READBACK-TRANSPOSE`

World requirement:

> A transposed or sliced view reads back according to its index mapping and remains valid for its declared lifetime, including when the original Python tensor reference is gone.

Shared phenomena:

- Base tensor and view construction.
- Storage identity and lifetime.
- View shape.
- Readback values.
- Errors.

This covers both mathematical view semantics and the earlier parent-lifetime defect.

## 4. Make ground truth an imported observation

Add a small observer pipeline:


Each observation must identify:

- Upstream revision.
- Tgrad subject tree.
- Dirty/clean status.
- Verifier tree.
- Adapter hash.
- Exact runtime artifact hash.
- Environment hash.
- Scenario manifest.
- Requirement IDs.
- Relation used.
- Raw result artifact.
- Validator and calibration version.
- Per-dimension results and relevant fault calibration.

Before promotion, extend this identity to hashes of the interpreted
requirement, profile, assumptions, relation semantics, and boundary
specification. IDs alone are not enough when those definitions can change.

The implemented deterministic status route is:

```text

  → Tgrad/Growth/PilotStatusMain.lean
  → Tgrad.Growth.PilotReport.reportJson
```

Its output should be generated, not authored:

```json
    "REQ-PY-IMPORT-HELPERS": {
      "specification": "specified",
```

## 5. Derive work from the result

The status compiler should emit gaps:

```text
GAP-PY-IMPORT-HELPERS
  kind: implementation
  blocks:
    - REQ-TENSOR-ADD-BROADCAST upstream observation
    - REQ-VIEW-READBACK upstream observation

GAP-ADD-UPSTREAM-OBSERVATION
  kind: evidence
  blockedBy:
    - GAP-PY-IMPORT-HELPERS
```

Then derive the work frontier:

```text
WORK-PY-COMPAT-HELPERS
  closes: GAP-PY-IMPORT-HELPERS
  oracle: isolated import scenario
  falsifier: poisoned upstream installation
  likely components: substitution shim / Python compatibility surface
  authoring resources: Python
  verification resources: CPU
```

The implemented `deriveHelperSurfaceWork` is only a conditional instantiation
of this authored packet schema. Components, resources, transitions, priority,
and recovery remain authored; applicability and the blocked count are derived.
Do not describe it as generic work selection until those choices are compiled
from typed obligations and resource facts.

No `goalDistance` is authored. Priority follows from:

- Number and importance of blocked requirements.
- Dependency position.
- Risk.
- Independent oracle strength.
- Cost.
- Scarce resources.

At the baseline, the authored schema ranked the helper boundary ahead of
another kernel operation. Because the candidate already existed and the schema
was repaired after observing the result, this was a retrospective ranking—not
prospective evidence of work-selection quality.

## 6. Falsify the method before trusting it

The method is not working merely because its Lean files compile. Run explicit mutations and require correct localization:

| Mutation | Required diagnosis |
|---|---|
| Change the upstream revision without regenerating manifests | Target becomes stale; product claims remain unchanged |
| Allow the strict shim to fall back to upstream tinygrad | Substitution validator rejects it |
| Remove required helper name `DEV` | Public-surface dimension fails while owned-module resolution still passes |
| Remove `tinygrad.helpers` mapping | Import requirement fails; add/view become blocked, not failed |
| Alter one broadcast stride | Add requirement fails; import and view remain unchanged |
| Drop view-parent retention | View-lifetime requirement fails |
| Change evidence `subjectTree` | Promotion becomes stale/invalid |
| Hand-edit a generated coverage/work output | Regeneration restores truth or audit rejects it |

The validator must also have at least one injected mutant it has observed red. This reuses the strongest idea already present in `Parity.lean`: calibrated evidence.

## 7. Replay one real change, then require a prospective cycle

Use `tinygrad.helpers` compatibility as the first rehearsal because it is:

- Real.
- CPU-only.
- Upstream-visible.
- Blocking 29 test files.
- Separate from ongoing renderer/runtime work.

The eventual prospective sequence must be:

```text
observe absence
→ derive gap
→ derive work packet
→ implement candidate
→ observe candidate
→ accept, reject, or retain an explicit unknown
→ recompute all dependent states
```

After the change:

- The import observation should move from `failed` to `passed_calibrated`.
- The requirement may move to `conformant` only after the upstream target is
  promoted and the `D ∧ S ⊨ R` adequacy obligation is accepted.
- Previously blocked tests should become executable.
- Some will probably move from collection errors to assertion failures.
- Those newly visible failures should generate new semantic gaps.
- No one should manually edit coverage cells or work priority.

The isolated prerequisite produced the expected after-state, and regeneration
now leaves the helper packet absent. However, the candidate predated the packet
and closure handling was repaired afterward. The full suite has not yet been
rerun, so collection-to-assertion transitions remain an open observation.

For the next add or view cycle, freeze and hash requirements, derivation logic,
observer, expected transition set, and baseline report before any candidate is
authored. Any post-result change to those artifacts invalidates the prediction
trial and starts a new baseline.

Moving from collection failure to assertion failure is progress even if the headline pass count remains zero. It increases observability.

## How we know the method is working

Use a predeclared scorecard.

### Grounding

- 100% of promoted claims identify exact requirement/specification semantics,
  target, subject, runtime artifact, verifier, adapter and environment revisions,
  plus source-to-binary provenance when a runtime binary participates.
- Stale or dirty-tree evidence cannot promote a clean-tree claim.
- Upstream inventories and product inventories are generated, not transcribed.

### Requirement quality

- Every requirement constrains observable world phenomena.
- Every requirement has explicit applicability and assumptions.
- Every requirement has an executable observation type and satisfaction
  relation; the current typed descriptors are only the first formalization step.
- Upstream symbols and tests are provenance, not the behavioral statement itself.
- Requirements modules contain no concrete product symbols.

### Diagnostic power

Given a failure, the model distinguishes:

- Requirement ambiguity.
- Domain-assumption failure.
- Boundary/specification failure.
- Product conformance failure.
- Observer failure.
- Calibration failure.
- Environmental block.

For the pilot, all mutations above must be localized correctly.

### Change sensitivity

After a relevant change:

- Exactly the affected cells change.
- Prerequisite-dependent cells unblock automatically.
- Unrelated cells remain stable.
- Stale evidence is invalidated automatically.
- New gaps appear without roadmap editing.

### Derivedness

The pilot must contain:

- Zero authored coverage verdicts.
- Zero authored completion claims.
- Zero authored goal-distance numbers.
- Zero evidence-existence roll-ups masquerading as successful observations.
- Zero derivation-source changes between the frozen pre-change and post-change
  observations of a prediction trial.

Agents may author requirements interpretations and candidate transformations. They do not author whether their candidates conform.

### Predictive utility

The helper rehearsal does not count as prospective evidence because the
candidate already existed. Before implementing the next add/view candidate, a
frozen model must predict that it will:

- change an exact requirement-state set;
- leave an exact unrelated-state set unchanged;
- require a declared component/resource class;
- expose specified downstream observers;
- not establish any stronger claim than its calibrated dimensions.

After implementation, observed results should match that prediction. If they do not, the assumptions or dependency model must be revised.

### Repeatability

Running status derivation twice against identical inputs must produce identical output.

Changing only:

- subject tree,
- upstream target,
- adapter,
- environment, or
- validator

must invalidate only claims depending on that identity.

## Next execution sequence

Proceed in this order. Each step has a closure predicate; “more code exists” is
never one of them.

1. **Land the pilot substrate.** Verify generated evidence drift, the strict
   no-fallback test, deterministic status output, and `lake build TgradSpec`.
   Merge only a clean branch. Closure: CI binds committed JSON to generated
   Lean, and the declared macOS/Python environment reproduces the exact helper
   observation and status report named here.
2. **Re-observe the public compatibility suite.** Run the frozen 34-file
   `api_surface` contract against `b1df552` (or its merge commit) in the same
   calibrated environment. Closure: every file has a revision-bound result;
   collection, assertion, timeout, harness, and environment outcomes remain
   distinct. Do not carry forward the old 0/34 denominator.
3. **Decide the helper adequacy and target-promotion obligations.** Interpret
   whether the finite helper boundary scenarios are sufficient for the stated
   world requirement and review the extracted upstream target. Closure: either
   an accepted argument with provenance or an actionable `unknown`/`refuted`
   result—never promotion merely because the test passed.
4. **Build the broadcast-add observer.** Compare substituted Tgrad with the
   pinned upstream behavior over the declared finite scenario domain and all
   required dimensions: value, shape, dtype, exception, and realization
   effects. Calibrate at least broadcast stride, dtype promotion, and exception
   mutations. Freeze the model and expected transitions first. Closure: the
   model correctly localizes every mutant and records a current result for
   `REQ-TENSOR-ADD-BROADCAST` without derivation-source changes.
5. **Build the view/lifetime observer.** Exercise transpose and slice readback,
   release the base Python reference, force buffer reuse where safe, and compare
   values, shape, exceptions, effects, and storage validity. Calibrate wrong
   index mapping and dropped-parent-retention mutations. Closure: a current
   result for `REQ-VIEW-READBACK-TRANSPOSE` with both fault classes caught.
6. **Evaluate the scale gate.** Compute the scorecard in
   [requirement_engineering.md](requirement_engineering.md#how-to-know-whether-the-method-is-working).
   Scale only if all three frames complete, at least six injected faults are
   detected and localized, work predictions are useful, and the maintenance
   cost is lower than raw-suite diagnosis.

### Parallel shape

Parallelize authoring by independent artifact and problem frame, not by arbitrary
file count:

- One lane may interpret upstream requirements and adequacy arguments.
- One may build the broadcast observer.
- One may build the view/lifetime observer.
- One may improve product code only after a derived packet names the gap.
- One integration owner controls generated evidence, promotion decisions, and
  the current status baseline.

All lanes declare their write sets and evidence dependencies before work. Keep
verification serial until the 141 fixed `/tmp/tgrad_*` paths are namespaced;
keep Metal performance runs serial even afterward because the GPU and runtime
state are shared. Prefer no more than three or four simultaneous worktrees on
this machine because each Lean build tree costs roughly 239 MB and local free
space is constrained. CPU-only observers that use `mktemp` and do not share a
generated output may run concurrently.

## The scale-up decision

Do not migrate the 590 inventory until all of these are true:

1. Three of three pilot requirements have executable observation types and
   satisfaction relations, not only typed descriptors.
2. Three of three have reviewed or checked `D ∧ S ⊨ R` arguments.
3. Evidence binds exact requirement/profile/assumption/specification semantics,
   subject, runtime artifact, adapter, verifier, and environment identities,
   plus source-to-binary provenance when a runtime binary participates.
4. Every mandatory dimension has an actual result and at least one relevant
   caught mutation; at least six predeclared faults are correctly localized.
5. At least one work packet is frozen before its candidate is authored.
6. Derivation source is unchanged between that packet's pre/post observations.
7. Predicted downstream unblocks equal actually executable observers/tests.
8. Three clean reruns produce byte-identical deterministic status/work output.
9. No manual status or priority edit is necessary.
10. Measured diagnosis time and decisions show the method is cheaper and clearer
    than raw-suite/manual-roadmap diagnosis.

0/3 adequacy arguments accepted, 0/3 claims promoted, 2/6 minimum mutations
caught, 0 prospective changes, 0/2 downstream unblocks executed, no generic
work selector, and no comparative cost measurement. This is intentionally not
