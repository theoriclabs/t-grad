## 2. Add the minimum specification kernel

Create:

```text
Tgrad/Requirements/
  World.lean
  Phenomena.lean
  Assumptions.lean
  Requirements.lean
  ProblemFrames.lean
  Obstacles.lean

Tgrad/Specification/
  Boundary.lean
  Adequacy.lean

Tgrad/Conformance/
  Claims.lean

Tgrad/Evidence/
  Observations.lean
  Promotion.lean
```

Enforce dependency direction:

```text
Requirements ──→ Specification
                      ↑
Product ───────→ Conformance ──→ Evidence ──→ Derived State/Work
```

Important constraints:

- `Requirements/*` must not import concrete Tgrad product modules.
- Requirements may mention Python calls, tensors, values, errors, effects and devices.
- They may not mention `UOp`, `Renderer`, `PythonFFI`, or particular files.
- `Conformance/*` is the bridge allowed to import both the abstract specification and concrete product.
- Evidence never directly changes requirement status; promotion derives it.

The initial core can remain small:

```lean
inductive Controller
  | environment
  | machine

structure Phenomenon where
  id : String
  controlledBy : Controller
  description : String

structure Assumption where
  id : String
  statement : String
  provenance : String

structure Requirement where
  id : String
  frame : FrameId
  profile : ProfileId
  monitored : List PhenomenonId
  controlled : List PhenomenonId
  assumptions : List AssumptionId
  relation : Relation
  provenance : List SourceRef

structure MachineSpec where
  id : String
  observes : List PhenomenonId
  controls : List PhenomenonId
  relation : Relation

structure AdequacyObligation where
  assumptions : List AssumptionId
  specification : SpecId
  requirement : RequirementId
  status : Epistemic AdequacyResult
```

`Relation` must begin as a typed descriptor—not another unstructured string.
For the pilot, a modest algebra is enough, but this does not yet make it an
executable relation over traces:

```lean
inductive Relation
  | importResolves
  | samePublicNames
  | exactTensor
  | numericalTensor (rtol atol : Float)
  | sameShape
  | sameDtype
  | sameException
  | sameEffects
  | conjunction (relations : List Relation)
```

Later this can graduate into propositions and executable semantics.

## 3. Model three pilot requirements

Choose three because they cross different problem frames and correspond to known real failures.

### A. Python substitution

`REQ-PY-IMPORT-HELPERS`

World requirement:

> Under the public-API profile, a client importing `tinygrad.helpers` after substitution resolves to Tgrad without silently importing upstream tinygrad and exposes the declared public names.

Shared phenomena:

- Module request.
- Resolution result.
- Exported names.
- Import exception.
- Provenance of loaded module.

Baseline diagnosis at `c465f89`: failed or absent under the earlier observer.

This captures the blocker that caused 29 collection failures in the `fdc741d`
measurement. The suite has not yet been rerun on the current observed subject.

### B. Broadcasted addition

`REQ-TENSOR-ADD-BROADCAST`

World requirement:

> For compatible input tensors, substituted `Tensor.add` returns a tensor with the same shape, dtype, values, exceptions, and realization-observable effects as the declared tinygrad profile.

Shared phenomena:

- Input values, shapes and dtypes.
- Operation arguments.
- Returned shape and dtype.
- Realized values.
- Exceptions.

Baseline diagnosis:

- Product implementation exists.
- Upstream-suite observation is blocked by substitution prerequisites.
- Independent NumPy/differential evidence may establish only a narrower semantic claim.

Current model-level diagnosis: a candidate is mapped, but broadcast addition
remains unobserved through this requirements observer. The prerequisite's
isolated pass does not imply that the upstream suite now reaches this behavior.

That distinction tests whether the model can say “implemented and locally observed, but not yet observed through the compatibility boundary.”

### C. View readback and lifetime

`REQ-VIEW-READBACK-TRANSPOSE`

World requirement:

> A transposed or sliced view reads back according to its index mapping and remains valid for its declared lifetime, including when the original Python tensor reference is gone.

Shared phenomena:

- Base tensor and view construction.
- Storage identity and lifetime.
- View shape.
- Readback values.
- Errors.

This covers both mathematical view semantics and the earlier parent-lifetime defect.

## 5. Derive work from the result

The status compiler should emit gaps:

```text
GAP-PY-IMPORT-HELPERS
  kind: implementation
  blocks:
    - REQ-TENSOR-ADD-BROADCAST upstream observation
    - REQ-VIEW-READBACK upstream observation

GAP-ADD-UPSTREAM-OBSERVATION
  kind: evidence
  blockedBy:
    - GAP-PY-IMPORT-HELPERS
```

Then derive the work frontier:

```text
WORK-PY-COMPAT-HELPERS
  closes: GAP-PY-IMPORT-HELPERS
  oracle: isolated import scenario
  falsifier: poisoned upstream installation
  likely components: substitution shim / Python compatibility surface
  authoring resources: Python
  verification resources: CPU
```

The implemented `deriveHelperSurfaceWork` is only a conditional instantiation
of this authored packet schema. Components, resources, transitions, priority,
and recovery remain authored; applicability and the blocked count are derived.
Do not describe it as generic work selection until those choices are compiled
from typed obligations and resource facts.

No `goalDistance` is authored. Priority follows from:

- Number and importance of blocked requirements.
- Dependency position.
- Risk.
- Independent oracle strength.
- Cost.
- Scarce resources.

At the baseline, the authored schema ranked the helper boundary ahead of
another kernel operation. Because the candidate already existed and the schema
was repaired after observing the result, this was a retrospective ranking—not
prospective evidence of work-selection quality.

## 6. Falsify the method before trusting it

The method is not working merely because its Lean files compile. Run explicit mutations and require correct localization:

| Mutation | Required diagnosis |
|---|---|
| Change the upstream revision without regenerating manifests | Target becomes stale; product claims remain unchanged |
| Allow the strict shim to fall back to upstream tinygrad | Substitution validator rejects it |
| Remove required helper name `DEV` | Public-surface dimension fails while owned-module resolution still passes |
| Remove `tinygrad.helpers` mapping | Import requirement fails; add/view become blocked, not failed |
| Alter one broadcast stride | Add requirement fails; import and view remain unchanged |
| Drop view-parent retention | View-lifetime requirement fails |
| Change evidence `subjectTree` | Promotion becomes stale/invalid |
| Hand-edit a generated coverage/work output | Regeneration restores truth or audit rejects it |

The validator must also have at least one injected mutant it has observed red. This reuses the strongest idea already present in `Parity.lean`: calibrated evidence.

## How we know the method is working

Use a predeclared scorecard.

### Grounding

- 100% of promoted claims identify exact requirement/specification semantics,
  target, subject, runtime artifact, verifier, adapter and environment revisions,
  plus source-to-binary provenance when a runtime binary participates.
- Stale or dirty-tree evidence cannot promote a clean-tree claim.
- Upstream inventories and product inventories are generated, not transcribed.

### Requirement quality

- Every requirement constrains observable world phenomena.
- Every requirement has explicit applicability and assumptions.
- Every requirement has an executable observation type and satisfaction
  relation; the current typed descriptors are only the first formalization step.
- Upstream symbols and tests are provenance, not the behavioral statement itself.
- Requirements modules contain no concrete product symbols.

### Diagnostic power

Given a failure, the model distinguishes:

- Requirement ambiguity.
- Domain-assumption failure.
- Boundary/specification failure.
- Product conformance failure.
- Observer failure.
- Calibration failure.
- Environmental block.

For the pilot, all mutations above must be localized correctly.

### Change sensitivity

After a relevant change:

- Exactly the affected cells change.
- Prerequisite-dependent cells unblock automatically.
- Unrelated cells remain stable.
- Stale evidence is invalidated automatically.
- New gaps appear without roadmap editing.

### Derivedness

The pilot must contain:

- Zero authored coverage verdicts.
- Zero authored completion claims.
- Zero authored goal-distance numbers.
- Zero evidence-existence roll-ups masquerading as successful observations.
- Zero derivation-source changes between the frozen pre-change and post-change
  observations of a prediction trial.

Agents may author requirements interpretations and candidate transformations. They do not author whether their candidates conform.

### Predictive utility

The helper rehearsal does not count as prospective evidence because the
candidate already existed. Before implementing the next add/view candidate, a
frozen model must predict that it will:

- change an exact requirement-state set;
- leave an exact unrelated-state set unchanged;
- require a declared component/resource class;
- expose specified downstream observers;
- not establish any stronger claim than its calibrated dimensions.

After implementation, observed results should match that prediction. If they do not, the assumptions or dependency model must be revised.

### Repeatability

Running status derivation twice against identical inputs must produce identical output.

Changing only:

- subject tree,
- upstream target,
- adapter,
- environment, or
- validator

must invalidate only claims depending on that identity.

## Frozen shape of the next prospective packet

not treated as a current normative requirement and not silently broadened or
declared superseded. The new independently decidable boundaries are:

| Requirement | Included behavior | Excluded behavior |
|---|---|---|
| `REQ-ADD-LEGAL-SAME-DTYPE` | exact value and shape for deterministic legal same-dtype addition, including right-aligned singleton broadcasting | dtype promotion, invalid shapes, gradients, symbolic/zero-size dimensions |

| `REQ-REALIZE-IDEMPOTENT` | `realize()` identity, repeat readback, and unchanged inputs for the declared finite scenarios | cache/performance and concurrency guarantees |

The finite scenario manifest is fixed prospectively to:

2. Singleton-axis f32 addition, `(2,3) + (2,1)`.
3. Right-aligned rank extension with i32, `(2,3) + (3,)`.
4. Two-sided broadcasting, `(2,1,3) + (1,2,1)`.
5. i32 Tensor plus a typed zero-dimensional f32 Tensor promotion case.
6. Incompatible shapes `(2,3) + (2,2)`, with construction and `.shape`
   observed separately so exception timing is part of the relation.

Every legal scenario records construction, pre/post shape and dtype, exact
values, `realize() is self`, repeated realization/readback, and unchanged
inputs. The incompatible scenario records exact stage, class, and message.

subtract; wrong right alignment; disabled singleton expansion; wrong dtype

the second readback changes; and the left input mutates. Each names target
scenarios plus dimensions that must differ, must remain equal, or may become
unobserved. A validator is not calibrated until all eight are rejected and
localized without changing unrelated requirement states.

### Non-negotiable architecture rules

1. **One-way authority.** Accepted target/profile/interpretation judgments are
   inputs. Coverage, status and completion are outputs.
2. **No same-transaction self-judgment.** Contract, adapter/relation,
   implementation and promotion-policy changes are separate transactions.
3. **One source for each fact.** JSON at process boundaries is canonical and
   content-addressed; Lean views are generated and never hand-edited.
4. **Foreign expected behavior.** The candidate path never computes expected
   output. Upstream execution or an independent mathematical semantics does.
5. **Exact identities.** Target, source closure, subject, built runtime,
   verifier, adapter, relation, scenario and environment are all bound.
6. **Derived work.** An agent may not declare a feature packet merely because
   it wants to edit a component. Packets close current typed obligations.
7. **Serial judgment.** Authoring may parallelize under disjoint leases;
   integrated verification, evidence mutation and promotion are serialized.
8. **No scalar parity score.** Reports show state vectors and missing
   obligations. A profile certificate is all-or-nothing over its closed scope.
9. **Adversarial distance.** A claim-bearing field is admissible only when it
   is imported from an independently fixed source, recomputed by a trusted
   verifier, survives a declared refutation campaign, or is an explicit
   versioned judgment that visibly narrows the rendered claim. An agent-written
   Boolean or status literal is never evidence for itself.
10. **Admission independent of implementation.** Profiles and scenario
    domains are derived from the promoted upstream target and accepted scope
    judgments, never from what Tgrad currently happens to run. If an admitted
    upstream program cannot run in Tgrad, the result is divergent or blocked,
    not silently excluded.
11. **Bounded evidence says bounded.** Finite tests, generated searches and
    mutation campaigns may justify `survivedSearch`; they do not become proofs
    by being placed in a certificate. Any release policy that accepts bounded
    evidence must say so and print its budget.
12. **Generated claims only.** Human-facing completion language is rendered
    from a reproducible canonical certificate. Documentation and release gates
    may reference that claim but may not independently say “complete”.

### Assurance semantics used by every phase

Do not use an unqualified `accepted : Bool` for adequacy or completion. The
epistemic result for an obligation is one of:

```text
open
blocked(environment-or-authority reference)
refuted(counterexample reference)
survivedSearch(search-certificate reference)
acceptedBy(judgment reference)
proved(proof reference)
```

`acceptedBy` records a real judgment without laundering it into a theorem.
`survivedSearch` records the generator identity, source closure, seeds, budget,
partitions, divergence count and mutation-calibration result. A profile owns a
versioned **assurance policy** mapping each obligation class to the minimum
acceptable state. Consequently, a profile may mechanically derive readiness
while still printing that some dimensions rely on bounded search or judgment.

Every claim-bearing field is classified as one of:

```text
imported     fixed by a promoted foreign source closure
derived      recomputed from imported inputs by an identified verifier
calibrated   supported by a recorded refutation/mutation campaign
judgment     accepted by named authority with explicit scope and invalidation
```

The verifier rejects unclassified fields. Git ancestry and hashes are useful
`derived` chronology evidence, but Git history is agent-authored and therefore
is not a foreign behavioral oracle.

### Phase M4 — Mechanize adequacy and requirement discharge

Purpose: close the Jackson/Zave argument for the first real requirements.

For each pilot requirement, represent:

```text
D  domain facts and accepted assumptions
R  world-visible required trace relation
S  complete-replacement boundary trace relation
```

Where feasible, prove `D ∧ S ⊨ R`. Otherwise record an explicit reviewed
adequacy argument with counterexamples considered and invalidation conditions.
Do not treat `BoundarySpec.structurallyCovers` as adequacy.

Adequacy challenges contain evidence references and executable predicates,
not authored `satisfiesSpec` or `violatesRequirement` Booleans. Challenges are
generated for every mandatory dimension, executed against upstream and the
specification, and calibrated with intentionally inadequate specifications.
Failure yields `refuted`; a finite successful campaign yields
`survivedSearch`; only a proof yields `proved`. A named authority may issue
`acceptedBy` when the profile assurance policy permits judgment, but the
renderer exposes that fact.

Then re-observe the current tree under the executable scenarios and derive the
first discharge candidates. A focused implementation regression can strengthen
the evidence without retroactively strengthening an older requirement.

Exit criterion: at least one narrow requirement has a valid real discharge
certificate, while the other pilot requirements remain mechanically open for
specific reasons. Deleting its adequacy record, one mandatory dimension, its
runtime attestation or one required environment makes the discharge invalid.
Replacing a proof with bounded search changes the rendered assurance grade and
cannot pass a profile whose policy requires proof.

- interpretation proposer;
- contract reviewer/adjudicator;
- observer and falsifier author;
- product candidate author;
- independent verifier;
- serial integrator/promoter.

Before an interpretation or scenario contribution can enter the accepted
catalog, a trusted acceptance harness verifies that its denotation runs against
upstream, upstream satisfies its own declared relation, all mandatory
dimensions are represented, declared dimension mutants are killed, replay is
deterministic, and the contribution transaction changed neither product nor
ontology files. Passing this harness establishes admissibility and calibration,
not behavioral completeness.

No product candidate branch may change its accepted contract, relation,
expected outputs, exclusions or promotion policy. No observer branch may
promote product conformance. Failures remain first-class artifacts.

Exit criterion: two disjoint packets are authored concurrently without shared
write/read effects, then integrated serially; neither agent edits a status
cell; one intentionally bad candidate is rejected and remains diagnosable.

### Phase M7 — Rewrite through vertical semantic slices

Purpose: use the mechanical loop to build the actual replacement.

The product order remains dependency-driven:

1. Python substitution and public construction/introspection.
2. Scalar/dtype semantics and host/storage representation.
3. Movement, indexing, alias and lifetime semantics.
4. One graph/compiler spine with a pure evaluator and CPU target.
5. Elementwise and promotion families through the spine.
6. Reductions and accumulation dtypes.
7. Matmul/convolution as semantic graphs; specialized WMMA as refinement.
8. Assignment, random and other state/effects.
9. Reverse-mode autograd.
10. TinyJit capture/replay/invalidation.
11. NN, state, serialization and selected workloads.
12. Multi-device and each explicitly selected backend profile.

Every slice crosses API, scenario semantics, graph, evaluator, compiler, CPU,
Metal where applicable, runtime safety, foreign tests and discharge evidence.
Horizontal substrate work is selected only when it immediately unblocks
multiple ready slices. A source symbol or emitted kernel is not an
implementation claim without a runtime trace through the declared path.

Exit criterion per slice: all newly applicable closed-scope requirements have
valid discharge certificates; unsupported partitions remain generated gaps;
the common-spine trace and backend-specific refinements are independently
observed.

### Phase M8 — Composition, performance and continuous tracking

Purpose: prevent locally complete operations from producing an incomplete
system.

Add stateful sequence and workload requirements for training steps, model
inference, serialization, JIT replay, alias/mutation sequences and device
failure/recovery. Generate interaction obligations from requirement-declared
phenomena and effects rather than a made-up full Cartesian matrix.

Performance remains a distinct certificate. Both tinygrad and Tgrad execute in
the same session with matching prepared boundaries; repeated sessions estimate
variance before any threshold is adopted. A semantic certificate and a
performance certificate may both be required by release policy, but remain
independent claims.

Finally, automate tracking mode:

```text
new tinygrad revision
-> source-closure diff
-> proposed interpretation changes
-> accepted new target
-> deterministic invalidation
-> typed gap/work frontier
-> restored profile certificate
```

Exit criterion: ingest a second tinygrad revision without changing ontology or
completion code; the system identifies additions, removals, semantic-review
questions and stale evidence, and reports a measurable compatibility lag.
The generated report distinguishes universal proof, accepted judgment,
bounded-no-divergence, blocked and refuted cells rather than flattening them to
one green percentage.

### Program-level success and stop rules

Proceed from the pilots to the full public contract only when:

- the synthetic completion certificate survives ordinary replay and all
  declared completion mutants are rejected;
- every claim-bearing field has admissible imported, derived, calibrated or
  judgment provenance;
- every promotion transition has a full-history freeze-integrity certificate,
  with mutation-and-revert and omitted-cycle mutants rejected;
- all current state cells are derived;
- target/source/catalog closure is mechanically total;
- at least one real requirement is discharged end to end;
- scenario admission is independent of Tgrad support, and bounded searches
  print their generator, seeds, budget and assurance grade;
- one real prospective agent packet is selected, implemented, rejected or
  promoted, and recomputed without manual status edits;
- evidence is reproducible and causally bound to its runtime;
- the next cycle costs less than reconstructing the same answer manually.

Redesign or stop scaling if agents routinely need to edit expected values or
status, catalog closure requires ontology changes for ordinary upstream drift,
mutants survive, product failures are confused with verifier/environment
failures, work packets predict the wrong causal boundary, or model upkeep
costs more than the ambiguity it removes. Also stop if a generated search can
avoid an admitted upstream partition, an evidence record can be promoted by
editing its conclusion fields, or bounded search is repeatedly presented as a
universal claim.

The final criterion is not that agents can write many lines of Tgrad. It is
that more agent search produces more independently discharged requirements on
a fixed target, while the checked system—not the agents—explains why each
claim is valid and what remains before profile completion.
