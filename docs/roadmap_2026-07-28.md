## 2. The structural finding that shapes everything below

Mining the promoted observation's captured stdout for what actually
blocks each file splits the 34 canonical files cleanly in two:

- **Tier A — 21 files, ~800 upstream passes at stake.** Blocked only by
  ordinary tensor API: `Tensor.pad`, `cast`, `contiguous`,
  `is_floating_point`, `log_softmax`, `cross_entropy`, `data`, and
  friends. No architectural gap. Reachable by incremental work.
- **Tier B — 12 files.** Blocked by capability Tgrad does not have
  *architecturally*: `TinyJit` (JIT tracing), `helpers.Context` /
  `ContextVar` (settings that must actually take effect), symbolic
  `Variable` (shape polymorphism), `llm.model.TransformerConfig` (a
  model zoo). These are not increments; each is a subsystem.

This is the most useful thing measured this week, because it makes a
bounded target defensible instead of arbitrary.

**The first file-level win is one method away, and it is verified.**
`test/backend/test_to_numpy.py` is a single test:

```python
output = Tensor.ones((1, 3, 4096)).realize().numpy()
assert out.shape == (1,3,4096) and (out==1).all()
```

Everything in that line except `Tensor.ones` already works today — I ran
the rank-3 f32 buffer, `realize()`, `numpy()` and the pickle round-trip
against the current build and they pass. **M0 is one classmethod.**

A methodological caveat worth recording, because it nearly misled this
document: **a small gap in pass-count is not a small gap in capability.**
`test/unit/test_shm_tensor.py` also shows "1 pass away", but that pass
needs `Tensor.randn`, `.nbytes()`, and `.to("disk:shm:...")` — a second
backend. Always read the test before ranking it. The ranked-blocker
mining in §2 is a search heuristic, not a work estimate.

## 3. On the rate, honestly

Recent cycles delivered small increments: five growth cycles produced +3
passing tests, and `default_int` produced +1. Extrapolating that against
800 Tier-A passes gives a number nobody should plan around.

But the extrapolation is probably wrong in a way that matters. Those
increments were narrow by construction — a single dtype default, a
single constructor split. A cycle that lands `Tensor.pad` or `cast`
plausibly unblocks tests in double digits, because those methods appear
across many files. **The rate for broad tensor methods is currently
unknown, and establishing it is M3's actual purpose.** Until three such
cycles have run, any parity ETA is fiction.

What can be said now: the current *cycle cost* is not economical, and
the requirements doc says so itself ("six protocol/tooling revisions
were needed before one upstream and one TGrad observation became
comparable... the cost is not yet proven economical"). Two full suite
runs plus baseline churn per increment does not amortise against +1
test. M2 exists because of this.

### M1 — Hygiene, time-boxed to one week
Three known defects that cost credibility every time someone looks.

1. **Legacy `gate_evidence` is decaying.** 26/37 files certify commit
   `a06d475cba26`, which is not in the repository; 78/115 recorded
   hashes resolve to nothing; 17 files were rewritten after generation.
   It also grows worse on its own as the tree moves. Either regenerate
   (a full serial GPU sweep) or **retire it explicitly**. Keeping
   unverifiable evidence beside the rigorous new tier drags the new tier
   down by association.
   **Exit:** `evidence_provenance_audit.py` exits 0, or fails only
   against an explicit quarantine list that is checked to be shrinking.
   The audit is wired into `devcheck` either way — today it is wired
   into nothing, which is why the rot was free to grow.
2. **L12 is red and its predicate is unsound.** It compares a live
   timing against a baseline read from a file recorded in another
   session, so it measures session drift as much as code. Redesign to
   run both sides in one session and report a distribution, or retire
   the perf claim.
   **Exit:** no gate is listed in `GREEN_GATES` while red.
3. **Cross-machine reproducibility.** `facts` still pins absolute
   interpreter paths, so the canonical score reproduces on this laptop
   only. The tokenization pattern is already proven on the pilot
   observer (`a350dbf`).
   **Exit:** a canonical pair certifies from a second checkout with a
   different absolute path.

### M2 — A cycle costs minutes, not a day
**Why:** this gates everything after it. At the current cost, M3 is
unaffordable regardless of how much capability is left to add.
**Work:** one entry point that runs observe → change → observe;
automatic re-baseline when the verifier changes (today a one-line
observer edit invalidates every baseline and forces two full runs);
batch observer changes rather than landing them singly.
**Exit:** measured wall-clock for a full cycle, recorded in the growth
log, under an agreed threshold. Pick the threshold from the M0/M1
measurements rather than inventing one now.

### M3 — Tier A bulk capability
**Work:** driven by the ranked blocker list, not by intuition. Current
top ordinary-API blockers by frequency: `Tensor.callify` (8),
`Tensor.pad` (7), `is_floating_point` (6), `cast` (5), `contiguous` (5),
`gradient` (5), `log_softmax` (5), `cross_entropy` (4), `data` (4).
Re-mine the ranking after every promoted pair; it moves.
**Exit (staged):** ≥5 of 34 files passing, then ≥10.
**Secondary exit, equally important:** three broad-method cycles
completed with measured deltas, so the Tier-A rate stops being a guess
and a real ETA becomes possible for the first time.

### M4 — Architecture go/no-go on Tier B
**This is a decision milestone, not a work milestone.** Tier B needs
lazy evaluation, JIT tracing, symbolic shape variables and a model zoo.
That is a different project from "add tensor methods."

Take the decision explicitly, in writing, with M3's measured rate in
hand. The options are real and none is embarrassing:
- commit to the subsystems and accept the timeline;
- **declare Tier A the target**, state publicly that Tgrad implements
  the non-JIT, non-symbolic subset of tinygrad's api_surface, and report
  parity against that denominator honestly;
- treat Tgrad as a result about method — verified prospective
  requirements engineering on a real codebase — and stop measuring it as
  a tinygrad replacement.

The failure mode to avoid is not choosing, and letting "full parity"
remain implied while the measured denominator quietly stays at 34 files.

### M5 — External reproduction
**Exit:** someone other than the author, on other hardware, reproduces a
canonical pair from a clean clone using documented commands. Until this
happens, every number in this document is self-reported. M1.3 is its
precondition.

## 5. Standing rules these milestones must not break

Earned the hard way; two were violated this month.

- **The shim may only EXPOSE capability Tgrad has. It must never
  implement upstream logic or fake a capability.** A no-op `Context`
  that swallowed `Context(DEBUG=2)` would turn Tier B green while
  changing nothing — manufacturing exactly the false positives the
  strict shim exists to prevent.
- **Equally: do not make honest answers fail.** Raising on `==` for an
  absent dtype looked like closing a false-positive hole; it destroyed
  16 real passes and 495 localized failures, and was reverted in
  `cdacef1`. "Not equal" is the *truthful* answer for a capability that
  is genuinely absent.
- **Regenerate evidence when the instrument changes, never when the
  result is inconvenient.** The distinguishing test: re-recorded
  calibration must reproduce the prior readings exactly. It did
  (33/34, 1145, 0).
- **A check that has never been shown red is not evidence.**
- **The foreign oracle's authority comes from not being authored here.**
  Keep it pinned, verified, and out of `/tmp`.
